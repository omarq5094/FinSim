# الصلاحيات التأسيسية

كل التفويض يعتمد على `workspace_memberships` داخل قاعدة البيانات، وليس user_metadata أو إخفاء الأزرار. العضوية تُقرأ من قاعدة البيانات في كل طلب، لذا إزالة العضو تسري دون انتظار تحديث JWT. المؤسسة هنا مساحة عمل في التطبيق، مستقلة عن مؤسسة استضافة Supabase.

| المورد / العملية | المالك | المدير المالي cfo | المحلل analyst | المشاهد viewer |
| --- | --- | --- | --- | --- |
| قراءة بيانات المؤسسة والشركات والمشاريع والسيناريوهات | نعم | نعم | نعم | نعم |
| تعديل اسم المؤسسة | نعم | لا | لا | لا |
| إضافة/تعديل/إزالة عضوية غير المالك | نعم عبر RPC | لا | لا | لا |
| إنشاء/تعديل الشركة ومشروع المحاكاة | نعم | نعم | لا | لا |
| إنشاء/تعديل السيناريو ومدخلاته في مشروع قائم | نعم | نعم | نعم | لا |
| قراءة سجل التغييرات | نعم | نعم | نعم | نعم |
| كتابة سجل التغييرات مباشرة | لا | لا | لا | لا |
| إنشاء نقاط حفظ/تشغيل تحليل | مؤجل | مؤجل | مؤجل | لا |
| حذف شركة/مشروع/سيناريو مباشرة | غير ممنوح | غير ممنوح | غير ممنوح | غير ممنوح |

ملف المستخدم خاص بصاحبه؛ يملك تعديل display_name فقط. يشارك UUID حسابه مع المالك ليضاف إلى المؤسسة؛ لا توجد دعوات بريد أو إرسال رسائل آليًا. يجب أن يسجل العضو الدخول مرة ليُنشأ ملفه. لا يوجد نقل ملكية في الأسبوع الأول؛ لا يمكن إزالة المالك أو ترقيته/تخفيضه عبر RPC الأعضاء.

## حدود الصلاحية

- كل جدول عام له RLS مفعّل ومفروض، وSELECT policy مناسبة. سياسات UPDATE تتضمن USING وWITH CHECK.
- لا توجد امتيازات للجداول أو RPCs لدور anon. authenticated لا يعني السماح لكل البيانات: السياسات تتحقق من العضوية والدور لكل صف.
- صلاحيات الأعمدة تمنع تعديل workspace_id أو العلاقات أو id أو صاحب المؤسسة أو الأختام الزمنية. الحذف غير ممنوح باستثناء إزالة عضوية غير المالك عبر إجراء مضبوط.
- مفاتيح خارجية مركبة `(id, workspace_id)` تمنع روابط بين مؤسستين حتى إذا كان المستخدم عضوًا في كليهما. parent_version_id مقيد أيضًا بنفس السيناريو والمؤسسة.
- `scenario_versions` أساس مخطط فقط، بدون كتابة من العميل أو تنفيذ حفظ/استعادة/تفرع. سجلات الإصدارات والأحداث لا تمنح UPDATE أو DELETE.
- تكتب triggers موثوقة أحداث التغييرات مع actor_id من auth.uid() ووقت قاعدة البيانات، دون نسخ افتراضات أو أسرار في سجل الأحداث.

## الإجراءات المميزة

الوظائف ذات SECURITY DEFINER محصورة في `finsim_internal` غير المكشوف لـData API، وتستخدم search_path فارغًا، وتتحقق من auth.uid(). جميع امتيازاتها الافتراضية مسحوبة، ولا يمنح EXECUTE إلا حيث يلزم. لا توجد وظيفة SECURITY DEFINER في public.

`workspace_role` يتجاوز RLS في جدول العضوية لتجنب استدعاء السياسات لنفسها، ويعيد دور المستخدم الحالي فقط. `create_workspace` يربط المالك بـauth.uid() وينشئ العضوية ذريًا، دون قبول owner_id من العميل. `set_workspace_member` يتحقق من مالك المؤسسة ويقفل صفها خلال التغيير. audit_change وظيفة trigger لا يمكن استدعاؤها مباشرة وتتحقق من العضوية قبل كتابة الحدث.

واجهات RPC العامة SECURITY INVOKER wrappers ذات GRANT صريح للمصادقين فقط. `create_scenario_draft` يعمل بصلاحيات المستدعي وينشئ المشروع والسيناريو والمدخلات ذريًا؛ المحلل يحتاج مشروعًا موجودًا لأن RLS يمنعه من إنشاء مشروع.

اختبرت هذه الصلاحيات محليًا داخل PGlite وعلى مشروع FinSim السحابي. نجح `scripts/sql/verify-cloud-security.sql` ثم أُلغيت بياناته بالـrollback. أعيد تشغيل Security Advisors وكانت النتيجة صفر أخطاء وتحذيرات وملاحظات. اختبار حفظ البيانات من واجهة مستخدم مسجل لم يكتمل بعد.
