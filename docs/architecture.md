# البنية وحدود المراحل

## الأسبوع الأول

التدفق: نموذج عربي ← Server Action تتحقق من المدخلات والهوية ← عميل Supabase بجلسة المستخدم ← RPC أو جدول تحت RLS ← عرض البيانات المحفوظة. لا يوجد مفتاح service_role في التطبيق، والذكاء الاصطناعي ليس مصدر الأرقام.

المؤسسة في التطبيق workspace، وليست مؤسسة استضافة Supabase. لكل workspace مالك ثابت وعضويات موثوقة بأدوار owner/cfo/analyst/viewer. [مصفوفة الصلاحيات](permissions.md) توضح الحدود.

## البيانات

| الجدول | الغرض |
| --- | --- |
| profiles | ملف ذاتي للمستخدم مرتبط بـauth.users، بلا بريد أو أسرار |
| workspaces | المؤسسة ومالكها الثابت |
| workspace_memberships | دور المستخدم في المؤسسة |
| companies | هوية الشركة ونشاطها وحجمها وعملتها SAR |
| simulation_projects | مجموعة دراسات تابعة لشركة |
| scenarios | سيناريو في حالة draft فقط |
| scenario_inputs | الافتراضات ووحداتها ونسخة المخطط |
| scenario_versions | بنية محجوزة لإصدارات مستقبلية مع parent_version_id |
| simulation_events | سجل append-only لتغييرات المسودات، صادر عن triggers |

كل كيان تشغيلي يحمل workspace_id. الروابط المركبة تمنع الشركة أو السيناريو من الإشارة إلى بيانات مؤسسة مختلفة. parent_version_id مقيد بنفس السيناريو والمؤسسة، وversion_number فريد داخله. لا توجد كتابة للعميل في جدول الإصدارات ولا وظيفة حفظ/استعادة/تفرع في هذه المرحلة.

الجداول القابلة للتعديل لها created_at وupdated_at تتحكم به قاعدة البيانات. الإصدارات والأحداث immutable ولذلك لها وقت إنشاء/حدث فقط. القيود تمنع المال السالب والوحدات غير الصحيحة والمدد غير المقبولة. الفهارس تغطي العضوية وروابط المؤسسة والمفاتيح الخارجية.

## الإجراءات

create_workspace ينشئ الملف عند الحاجة والمؤسسة وعضوية المالك ذريًا. set_workspace_member يتيح للمالك وحده إدارة العضويات غير المالكة. create_scenario_draft إجراء SECURITY INVOKER ينشئ المشروع عند الطلب، ثم السيناريو ومدخلاته في معاملة واحدة؛ فشل أي إدخال يلغي العملية والأحداث الناتجة عنها. المحلل يحتاج مشروعًا قائمًا.

الوظائف المميزة موجودة في finsim_internal غير المكشوف؛ الأسماء مؤهلة وsearch_path فارغ وauth.uid يتحقق منه في وظائف التفويض. لا تستند الصلاحيات إلى user_metadata. لا توجد وظائف SECURITY DEFINER في public. لا توجد REST API مخصصة أو مستودع بيانات يحتفظ بحالة مشتركة بين المستخدمين.

## المال والحتمية

الإدخال العشري يحول نصيًا بـBigInt إلى هللات دون ضرب عشري عائم. سقف الحقل 9,999,999,999.99 ريال يبقي النقل الرقمي ضمن حد الأعداد الصحيحة الآمنة. محرك المحاسبة لاحقًا يستخدم bigint وقاعدة تقريب صريحة للتجميع الكبير والنسب.

العائد السنوي المستهدف بنقاط أساس؛ 18% = 1800. الإيراد والمصروف شهريان والمدة 1–120 شهرًا. لا يشتق التطبيق ضرائب أو تمويلًا أو تحصيلًا أو موسمية تلقائيًا. كل افتراض يستلزم توثيقًا. SimulationInputV1 عقد إدخال فقط، بلا ساعة أو تنفيذ.

## التوسع

الأسبوعان 2–3: دليل الحسابات والقيود ورؤوسها وأسطرها والأستاذ. كل جدول يحمل workspace_id وروابط مركبة. الترحيل ذري ومتوازن وله مفتاح منع التكرار؛ التقارير مشتقة من سجل محاسبي حتمي. اختبارات التوازن والأرصدة والتقارير والتقريب قبل AI.

الأسبوعان 4–5: العملاء والموردون والموظفون والمخزون، وأحداث تشغيلية تنتج قيودًا بقواعد حتمية.

الأسبوع 6: runs بنسخة محرك وبذرة صريحة وسجل أحداث مرتب وزمن محاكاة مستقل. snapshots وparent_run_id لإعادة التشغيل والرجوع والمسارات البديلة. جداول الإصدارات الحالية تهيئ البنية فقط؛ لا تنفذ هذه المزايا الآن.

الأسبوعان 7–8: واجهة CFO ورسوم تفاعلية وقرارات ومراجع يشرح الدليل والافتراضات. المراجع يقرأ تقارير موثقة ولا يملك صلاحية تعديل الأرصدة أو ترحيل القيود.

الأسبوع 9: اختبارات سيناريوهات وأداء وأخطاء ونسخة تجريبية. Vercel مؤجل.

## مثال الرياض لاحقًا

المدخلات المعروفة: استثمار أولي 850,000 ريال، عائد مستهدف 18%، مخاطرة مرتفعة. الواجهة تسمي العائد سنويًا صراحة؛ الفترة الأصلية للمثال غير محددة وتحتاج تأكيدًا قبل التحليل.

التدفقات والسيولة والحساسية تحتاج توزيع الاستثمار والتكاليف والإيرادات وتوقيت التحصيل والسداد والمخزون والتمويل والضرائب ورأس المال العامل. لا نختلق هذه الأرقام الآن. الاختبار الحالي يثبت تحويل المدخلات فقط، ولا يمثل دراسة جدوى.
